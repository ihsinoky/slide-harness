# レンダリング仕様（スライドの完成形）

スライドの完成形は HTML である。`slides.md` は内容の正（タイトル・図の指定・要点）であり、成果物はそれをレンダリングした `slides.html` とする。テキストベースで止めない。

## 成果物
- `works/<案件>/slides.md`：内容仕様（従来どおり）
- `works/<案件>/slides.html`：完成スライド。単一ファイルで完結させる（CSS・JS・SVG はすべて埋め込み、外部依存なし。オフラインで開けること）

## 資料の3層（内容・構造・表現）

資料は、文書工学で一般的な「内容・構造・表現」の3層でできている（SGML／Web 標準の系譜の分離）。

1. **内容**（案件ごと）：タイトル・図の中身・要点。案件ごとに作る素材で、`slides.md` が正
2. **構造**（フェーズ1で設計）：その資料の情報の編成。スライドの並びと階層（outline）と、スライド内でどの図の形に情報を組み立てるか。型とフェーズ1が担い、テンプレートでは変えない
3. **表現**（差し替え可能）：色・書体・余白・レイアウトという見せ方。テンプレートが担い、下記の解決順で差し替える。拡張とインポートの対象はこの層だけ

この3層の外に、層を横断する**規約**がある（`core/conventions.md`）。図解ガイドは規約の1つであり、層ではない。

## テンプレートの解決順（表現層）
レンダリング時は次の順でテンプレートを探し、最初に見つかったものを使う。使ったテンプレート（拡張デザインの場合は拡張名と版も）を lint-report に記録する。
0. 拡張デザイン：案件が指定した、検証を通った拡張（`extensions/<名前>/designs/<slug>/`、`core/extensions.md`）のデザイン
1. 案件固有：`works/<案件>/template/`（その案件専用の指定がある場合）
2. リポジトリ共有：`templates/` 直下に案件が指定するもの
3. 標準：`templates/standard/`（IBM Carbon Design System のトークンに基づく標準テンプレート）

テンプレートは「型」と直交する層である（形式制約・設計原則と同じ）。テンプレートの差し替えで内容（タイトル・図・要点）は変えない。

## 標準テンプレート（IBM Carbon 準拠）
- 採用経緯：2026-11-16、DADS／GOV.UK／USWDS／Carbon／Material 3／Fluent 2 の6標準で同一デッキを比較レンダリングし、利用者が Carbon を標準に選定した。DADS 版は `templates/dads/` に案件用として残す
- キーカラー：Blue 60 `#0F62FE`。淡色背景：Blue 10 `#EDF5FF`。本文 Gray 100 `#161616`、補助 Gray 70 `#525252`、罫線 Gray 50 `#8D8D8D`、フォーカス `#FFD43D`
- 書体：IBM Plex Sans JP（システムフォントへのフォールバック付き）
- スライド寸法：16:9（1280×720 を基準単位とし、表示はビューポートにフィット）
- 操作（スライドショー）：矢印キー／スペース／クリックで前後移動、Home／End で先頭・末尾、スライド番号と進捗表示、全画面表示、一覧（サムネイル）表示（ボタンまたは O キー）、印刷時は全スライド縦並び（@media print、操作 UI は出ない）
- 編集（編集モード）：ツールバーの「編集」で切り替える、単一ファイル内で完結するスライドエディタ。要素をクリックで選択し、ドラッグで移動（矢印キーで微調整、Shift で大きく）。プロパティパネルでテキスト内容・文字サイズ・文字色・塗り／線の色と太さ・四角の幅と高さ・位置（X/Y）を編集でき、要素の複製・削除もできる。図への要素追加（テキスト／四角／矢印）、本文と図内文字のダブルクリックでのインライン編集、スライドの追加・複製・削除・並べ替え（左パネル）、元に戻す／やり直し（Ctrl+Z／Ctrl+Y）に対応する。編集結果は「HTMLで保存」で単一ファイルとして書き出せる（外部依存なしを保つ）
- アクセシビリティ：テキストと背景のコントラスト比 4.5:1 以上を保つ。色だけで意味を伝えない（ラベルや形を併用する）

## 図解の作法（図解規約：図解ガイド＝figure-docs）
図解の作法は、カスタムスキル **figure-docs**（u-ichi/agent-plugins、2026-11-15 導入）を図解ガイドとして採用する。以下はその要点で、視覚 lint の判定基準にもなる。詳細と見本（事業の図112種・開発の図38種）はスキル本体を参照する。
- 形の選び方：言いたいことを1文に決める → 何を比べ・見せるかを分類から決める → 見本から形を選ぶ（形から先に決めない。Zelazny の順）
- 図の中の文字は、部品の名前と値と数語の注記だけにする。文を四角に詰めない（文は要点1行か注記へ）
- 1枚の図の四角は6つまで。超えるなら範囲を分けるか連作にする
- どの四角も矢印か入れ子でつなぐ。つながらない四角は描かない
- 矢印には、何を渡すかを書く。同期・順方向は実線、応答・非同期・フィードバックは点線
- 変更の前と後は同じ配置で並べ、差分だけ印を付ける
- 対応関係は、2つの図を矢印でつなぐのではなく、共通の軸（列）に対して帯の位置と長さで示す（対応図／マトリックス）。矢印は「対応」を表せない（2026-11-16、利用者の手本で是正）
- 3段階以上の移行や部品の追加は、同じ配置の連作で1つずつ足す
- 出す前のセルフチェック：文章を消しても、図だけで言いたいことが分かるか
- 色は意味で使い分け、色数を絞る。注釈は関係する要素の近くに短く置く。目線の流れ（左→右、上→下）に逆らわない

（経緯：当初「u1氏の図解ノウハウを参考に」と指示されたが、2026-11-16 に利用者が u-ichi の figure-docs のことだと訂正した。u1（Yuichi Uemura）氏の投稿に図解ガイドは無い。以後の図解ガイドは figure-docs で固定する）

## 図解の実装ルール
- 図は outline が指定した形を、インライン SVG または HTML/CSS の構造図として実際に描く。図のプレースホルダや「図：〜」という文章で済ませない
- 図の中のテキストはスライド本文と矛盾させない。数値・固有名は slides.md の記述と一致させる
- 図の部品にはラベルを付け、色分けには凡例か直接ラベルを併用する（色のみで区別しない）
- 1スライドの情報量：図が主、文章は要点1行＋補足まで。図の中に長文を詰め込まない

## 視覚 lint（フェーズ2の lint に追加する層）
- [ ] 機械 lint（`tools/lint-slides.py`）がパスしたか。図内テキストのはみ出し・重なりと構造の一致は、目視ではなく機械の実測で判定する（G2 の前提条件。pre-commit フックでも強制される）
- [ ] 全スライドを画像化し、全枚を1枚ずつ目視したか（機械で判定できないもの：読み違える図、図と文章の食い違い）。全枚が対象になるのは初回 G2 と G3 の節目で、部分確認をもって全枚パスと記録しない。変更ラウンドでは変更したスライドだけを目視し、その範囲を記録する（2026-11-17 に全枚目視を追加した失敗＝10枚目のはみ出し見落としは、v2.4 で機械 lint が実測担保するようになったため、目視の全枚義務は節目に限定した。プロセス v2.6）
- [ ] outline の図指定どおりの形で実際に描かれているか（全枚同型への退化がないか）
- [ ] 図解ガイド（figure-docs）への適合：四角の中に文が詰められていないか／四角が6つを超えていないか／矢印に「何を渡すか」が書かれているか／つながらない四角がないか／文章を消しても図だけで言いたいことが分かるか
- [ ] 図内テキストと本文・数値が一致しているか
- [ ] テンプレートの解決順に従い、使用テンプレートが記録されているか
- [ ] コントラストと文字サイズが標準テンプレートの基準を満たすか（テンプレート側の担保＋個別の逸脱チェック）
- [ ] 単一ファイルで完結し、外部リソース参照がないか
