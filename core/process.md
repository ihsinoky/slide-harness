# スライド作成プロセス（共通ソース）

スライド資料の作成を、AI-DLC のようにフェーズ・ゲート・成果物で組み立てたプロセス。
どの実行環境（GitHub Copilot / M365 Copilot Studio / その他）でも、このファイルが正。
各環境のバインディングは、この内容をその環境の流儀に写したものにすぎない。

## 大原則

1. **圧縮は意図合わせの後**。素材の要約・タイトル付けは、言いたいことの優先順位が人間と一致してから行う。
2. **フェーズを飛ばさない**。ゲート未通過では次フェーズに入らない。差し戻しは成果物単位で行う。
3. **生成と検査は別のパス**。作った本人がそのまま添削しない。検査はチェックリストに基づき、独立した視点で実行する。
4. **1スライド＝1メッセージ**。タイトルは名詞題ではなく主張文。
5. **図が先、文章は後**。文章は図ごとの要点1行＋畳んだ詳細。

## フェーズとゲート

### フェーズ0：意図

- 目的、読み手、「この資料で何を決めてほしいか（決まらない資料なら何を持ち帰ってほしいか）」を固定する。
- 素材は要約せず全部出す（拡散フェーズ。ここでは圧縮しない）。
- 言いたいことの候補を列挙し、数値スコア（1–10）で順位をつける。
- **ゲート G0**：優先順位マップを人間が確認し、ズレを直して承認する。ここが手綱の要所。

成果物：`intent.md`（目的・読み手・判断ゴール）、`priority-map.md`（スコア付きの言いたいこと一覧）

### フェーズ1：構成

- 優先順位マップから、1スライド＝1メッセージでアウトラインを作る。
- 各スライドのタイトルは主張文で書く（例：「市場は年11%で伸びている」。「市場の現状」は不可）。
- 各スライドについて、図の形を先に選ぶ（分類は `figure-forms.md`）。
- **並びはフェーズ順ではなく、読み手の疑問の鎖（でもチェーン）で決める**。各スライドは、前のスライドを読んだ読み手に生まれる次の疑問（「でも、〜だったら？」）に答えるものとして置く。仕組みやフェーズの都合で並べると機能紹介になり、必然性が消える（試走1号の教訓）。
- 各スライドに「前のスライドから生まれる疑問」を明記する。鎖の切れ目は G1 で見える形にする。
- **ゲート G1**：タイトルだけを並べたアウトラインを人間が承認する。構造の問題はここで潰す（最も安い差し戻し点）。

成果物：`outline.md`（タイトル一覧＋各スライドの図の形＋前のスライドから生まれる疑問）

### フェーズ2：生成

- 図を先に描く。文章は要点1行を添え、詳細は畳む（付録・ノート・展開セクションへ）。
- **図の形は outline の指定どおりにスライドごとに描き分ける**。全スライドを同じ図の型（例：横流れのフローチャート）に寄せない。生成は指定を無視して型を揃えがちで、試走1号ではそれが lint ラウンド1の全枚差し戻しの主因になった。
- 生成が終わったら、別パスで anti-slop リント（`anti-slop-checklist.md`）を実行する。
- **ゲート G2**：リント全項目パス。不合格は該当スライドだけ差し戻す。

成果物：スライド本体（形式は環境依存）、`lint-report.md`

### フェーズ3：検証

- コールドリード：タイトルだけを順に読んで、話が通るか確認する。
- 数値・事実を出典と照合する。
- **ゲート G3**：人間が最終承認する。

成果物：確定版スライド、検証メモ

## 役割

- 人間：G0 / G1 / G3 の承認者。優先順位の最終決定者。
- エージェント：拡散、順位付けの叩き台、構成、生成、リント、照合の下準備。
- エージェントが勝手に決めてよいのは、ゲートで承認された範囲の中の表現だけ。
