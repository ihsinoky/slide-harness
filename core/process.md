## 大原則

1. **型は G0 で確定する**。資料の型（主型・副型）が、スコア基準・構成の足場・検証の力点をすべて決める。型が違う資料に同じ物差しを当てない。ただし型の推定自体はエージェントの仕事であり、人間に類型の知識で判断させない。推定の前提は具体物の形で示し、G0 の確認ラリーで修正する。
2. **圧縮は意図合わせの後**。素材の要約・タイトル付けは、言いたいことの優先順位が人間と一致してから行う。
3. **フェーズを飛ばさない**。ゲート未通過では次フェーズに入らない。差し戻しは成果物単位で行う。
3b. **前提が崩れたら、承認済みでもフェーズを戻す**。ゲート通過後に前提（対象の版・公式構造・主題の理解など）の誤りが判明したら、差分の継ぎ接ぎで誤魔化さず、影響するフェーズまで戻って outline から作り直す（試走3号の教訓、2026-11-16：G3 承認後に AI-DLC のフェーズ数の前提誤りが判明し全面改訂した。9枚目も旧構成の仕組みのままだったため、フェーズを戻して新 outline の承認から作り直した）。戻す判断と影響範囲は記録する。
4. **生成と検査は別のパス**。作った本人がそのまま添削しない。検査はチェックリストに基づき、独立した視点で実行する。
5. **1スライド＝1メッセージ**。タイトルは名詞題ではなく主張文。1枚に主張は1つだけ（「〜し、〜する」式に2つの主張を1枚へ詰めない）。
5b. **ストーリーラインを初期に確立する**。スライドは主張という「点」の集まりではなく、点が一本の「線」としてつながった物語として設計する。各スライドの主張（点）と、前の主張からその主張へ進む接続（疑問・対比・因果・展開）を、フェーズ1の冒頭で `storyline.md` として書き切り、G1 で線として承認する。生成後に構成の必然性が崩れて見つかると、最も高い差し戻し（フェーズを戻しての全面改訂）になる。線を先に固定するのが最も安い。
6. **図が先、文章は後**。文章は図ごとの要点1行＋畳んだ詳細。
7. **検査と再読の範囲を最小にする**。従量制の実行環境では、消費は「1回の読みの単価 × パスの数」で決まる。lint は層ごとに読み直さず単一パスで判定し、変更ラウンドの再検査は変更範囲に限る。全量の再読は、初回 G2 と G3 の節目だけにする。範囲を絞る代わりに、機械で判定できるもの（構造の一致、はみ出し・重なり）は機械 lint が常時担保する。

## 更新（変更要求）の扱い

完成済み・作業中の案件に変更要求が来たら、まず変更の種類を判定し、戻り先を決めてから着手する。判定と戻り先は案件フォルダに記録する（変更履歴）。迷ったら大きい方の戻り先に倒す。

1. **表現の変更**（文言・図の微修正で、主張と構成は不変）：フェーズ2の該当スライドだけを作り直し、lint を再実施する。ゲートは G2 のみ
2. **構成の変更**（スライドの追加・削除・並べ替え、主張の追加・削除）：G1 まで戻る。outline を更新し、再承認を受けてから生成に入る
3. **意図の変更**（読み手・成功条件・型・主題の範囲の変更）：フェーズ0（G0）からやり直す。既存の成果物は破棄せず、素材として再利用する

前提の誤りが判明した場合は、大原則 3b（承認済みでもフェーズを戻す）に従う。

人間の指摘への対応は、個別修正で終わらせない。同じ指摘が他の資料でも起きうる形（パターン）に一般化し、指摘ナレッジ（`core/review-feedback.md`）への追加を検討する。追加した場合は、案件の記録にその旨を残す。

## ロール（mob）

AI-DLC の mob の考え方を、型に合わせて変形したもの。型のミッションはフェーズを跨いで保持すべきものなので、型リードは全フェーズに常駐するロールとする（AI-DLC のステージ固有エージェントからの意図的な逸脱）。

- **ファシリテータ**（進行役）：フェーズ0のヒアリングで型を推定し、G0 の確認ラリーを回す。型リードが確定するまでは暫定の主型で進め、型が差し替わったらリードも組み替える。
- **主型リード**：その資料の主型のロール定義（`core/type-leads/`）を持つ。プロセス全体の主導者。スコア基準、構成の足場、検証の力点は主型が決める。G0 承認で確定する。
- **副型リード**：副型のロール定義を持つ（副型は最大1つ）。候補の追加、チェーンのレビュー、副型の成功条件の確認を担う。実行は主導しない。
- **人間**：G0 / G1 / G3 の承認者。優先順位と型の最終決定者。
- エージェントが勝手に決めてよいのは、ゲートで承認された範囲の中の表現だけ。

主・副の競合ルール：副型の要素は、主型の成功条件を損なう場合は落とす。判断は主型リードが行い、落とした要素と理由を成果物に記録する。主型側でも決められないものは、ゲートで人間に上げる。

## フェーズとゲート

### フェーズごとの読み込み範囲（コンテキストの節約）

引き継ぎは会話ではなく成果物で行う。フェーズごとに新しいセッションで始めてよく、その場合は当該フェーズに必要なファイルだけを読む。全 core を毎回読み直さない。

| フェーズ | 読むもの |
|---|---|
| 0 | deck-types.md、主型候補の型リード（推定に使う分だけ） |
| 1 | intent.md、priority-map.md、確定した主型・副型の型リード、figure-forms.md |
| 2（生成） | storyline.md、outline.md、rendering.md、テンプレート |
| 2（lint） | slides.md／slides.html、anti-slop-checklist.md、主型・副型の型固有 lint、review-feedback.md、採用した拡張の規約 |
| 3 | 完成形、storyline.md（照合用）、intent.md（成功条件） |

### フェーズ0：意図（ヒアリング＋型の推定＋G0）

**ヒアリングと型の推定**（承認対象ではない、エージェント側の作業）

- ファシリテータが、目的・読み手・「この資料で何を決めてほしいか（決まらない資料なら何を持ち帰ってほしいか）」を聞き取る。聞くのは読み手と成功条件であって、型の名前ではない。人間に類型の用語で考えさせない。
- 聞き取りと初期素材から「読み手の仕事テスト」（この資料が成功したとき、読み手は具体的に何をした／何を持ち帰った状態になるか）で、主型1つ・副型0〜1つを推定し、プロセス計画（力点を置くフェーズ、有効化する型固有 lint、典型構成を足場にするか）と一緒に `type-diagnosis.md` に記録する。この時点の型は暫定であり、承認を取らない。
- 型の候補は core の7型に、検証を通った拡張（`extensions/`、`core/extensions.md`）の型を加えたものとする。拡張の型を使った場合は、拡張名・版・status を `type-diagnosis.md` に記録し、`sample`／`trial` の型はその旨を G0 の提示に含める。
- 素材は要約せず全部出す（拡散フェーズ。ここでは圧縮しない）。
- 言いたいことの候補を列挙し、暫定の主型リードのスコア基準で数値スコア（1–10）を付けて順位をつける。副型リードは副型の観点からの候補を追加し、`priority-map.md` に「副型候補」と明記する。

**ゲート G0（ファシリテーションで回す）**：ここが手綱の要所。型を決めても、認識違いによってイメージが合わないことは頻発する前提で、エージェント側が次の手順で能動的に擦り合わせる。単に「承認しますか」と聞いて終わりにしない。

1. **前提を具体物の形で示す**：優先順位マップの提示時に、前提とした型を平易な言葉で明示する（型の名前だけでなく「この並びは、読み手が参加するかを判断する資料として組んだ」のように、読み手の仕事として述べる）。あわせて、最も近い対抗仮説の型では順位がどう変わるかを1つ示す（上位候補の入れ替わりで見せる）。提示は常にマップ全体で行う。差分だけでは全体の並びが判断できない（試走2号の G0 で「優先順位全体が見えません」と差し戻された。同じ原則は G1 の目次提示にも適用する）。
2. **成功条件を人間の言葉で言い直させる**：エージェントが成功条件を言い直して提示し、人間の言葉とのズレをその場で拾う。ズレは項目レベルの修正ではなく、型レベルの不一致の兆候として扱う。
3. **修正の束を型の兆候として読む**：人間の修正が、対抗仮説の型なら上位に来るはずの候補に偏って集まる場合、項目を個別に直す前に「前提の型が違うかもしれません」と名指しし、その型で組み直したマップとの差分（何が上がり、何が下がり、なぜか）を提示する。
4. **修正ループ**：型が差し替わったら、主型・副型リードを組み替え、優先順位マップを作り直して再提示する。G0 での型の差し替えは失敗ではなく想定内の動作であり、ここで直すのが最も安い。イメージが合うまでループし、合った時点で intent・型・優先順位マップをまとめて承認する。

成果物：`type-diagnosis.md`（推定した主型／副型と根拠、対抗仮説、プロセス計画、G0 での差し替え履歴）、`intent.md`（目的・読み手・判断ゴール）、`priority-map.md`（スコア付きの言いたいこと一覧、副型候補を含む）

### フェーズ1：構成（ストーリーライン → アウトライン）

**手順1：ストーリーラインを確立する**（`storyline.md`）

- 優先順位マップから、まず図も詳細も書かず、主張の列だけを書き切る。各行は「主張（＝そのスライドのタイトル文）」と「接続（前の主張から、なぜこの主張へ進むのか）」の組にする。接続の形は疑問・対比・因果・展開のいずれかで、主型リードの「典型構成と疑問チェーン」をパターンとして使う（例：決断提案型なら反論処理の「でもチェーン」、成果・検証報告型なら検証の順序）。
- 書き切ったら、テキストだけで次の3つを判定する（この段階の検査は安い。ここで潰すのが最も安い）。
  1. **単一主張**：1行に主張が2つ入っていないか。入っていたら行を分ける（スライドも分ける）。
  2. **接続**：すべての接続が言葉で書けるか。書けない接続は鎖の切れ目であり、間の主張が要るか、並びが違う。
  3. **通読と着地**：主張だけを順に読んで一つの話として通るか。最後の主張が、主型の成功条件（決めてほしいこと、持ち帰り、入口など）に着地しているか。
- **並びはフェーズ順や仕組みの都合で決めない**。作り手の分類順に並べると機能紹介になり、必然性が消える（試走1号の教訓）。

**手順2：アウトラインを作る**（`outline.md`）

- ストーリーラインの各行に、図の形（分類は `figure-forms.md`）を割り当てる。主張と接続はストーリーラインから変えない。変える必要が出たら、それは構成の変更としてストーリーラインから直す。
- 副型リードは、副型の要素を独立パートとして置くか各スライドに織り込むかを提案し、接続の切れ目をレビューする。
- **ゲート G1**：ストーリーライン（線）を先に示し、続けてアウトライン（タイトル一覧＋図の形）を人間が承認する。構造の問題はここで潰す（最も安い差し戻し点）。

成果物：`storyline.md`（主張と接続の列）、`outline.md`（タイトル一覧＋各スライドの図の形＋前のスライドから生まれる疑問）

### フェーズ2：生成

- 図を先に描く。文章は要点1行を添え、詳細は畳む（付録・ノート・展開セクションへ）。
- **大きな描き直しは、代表スライドで先に方向を確認してから全枚へ展開する**。図の作法の変更や全面改訂では、まず代表の数枚（例：全体地図・対応表・仕組み図）を作って人間の確認を取り、方向が固まってから残りへ広げる（試走3号の figure-docs 適用で有効だった進め方、2026-11-16）。
- **図の形は outline の指定どおりにスライドごとに描き分ける**。全スライドを同じ図の型（例：横流れのフローチャート）に寄せない。生成は指定を無視して型を揃えがちで、試走1号ではそれが lint ラウンド1の全枚差し戻しの主因になった。
- 内容（`slides.md`）が固まったら、レンダリング工程で完成形の HTML スライド（`slides.html`）を作る。仕様は `core/rendering.md`：テンプレートの解決順に従ってテンプレートを選び、図は outline の指定どおりに実際に描く（図の文章説明で済ませない）。テキストベースで止めることは未完成として扱う。
- 生成が終わったら、別パスで lint を実行する。**lint は単一パスで実行する**：スライドを1回読み、内容の3層（共通 anti-slop（`anti-slop-checklist.md`）、主型 lint、副型 lint（各型リードの「型固有 lint」））と、指摘ナレッジ（`core/review-feedback.md`）の全パターン、採用した拡張の規約を、層別の節を持つ1つの lint-report にまとめて判定する。層ごとに別パスで読み直さない（大原則7）。共通 anti-slop の「メッセージと読み手モデル」の節は全スライド必須の検査であり、図だけでの主張の言い直し、読み手の出発点との接続、既出の図との配置の一致、内部用語の有無をスライドごとに判定して記録する。あわせて、各スライドのタイトルと図が `storyline.md` の自スライドの主張と一致しているか（主張の忠実度）を判定する。
- 機械 lint（`tools/lint-slides.py`）を必ず実行し、終了コードと出力を lint-report に記録する。機械 lint が不合格なら、他の層の判定にかかわらず G2 はパスできない。使用したテンプレートを lint-report に記録する。
- 視覚 lint（rendering.md）の全枚目視は、**初回 G2 と G3 の節目だけ**を全枚対象とする。はみ出し・重なりは機械 lint が全ラウンドで担保するため、目視の範囲を絞ってもその安全性は落ちない。変更ラウンドでは、変更したスライドだけを画像化して目視する（v2.3 追記の全枚目視は、機械 lint が無かった前提の防御であり、v2.4 以後は役割を機械 lint へ移した）。
- **差分 lint**：変更ラウンドの再検査は、変更したスライド＋ストーリーラインとの整合＋機械 lint に限る。全層のフル lint は初回 G2 の1回だけとする。修正は指摘を集めてから1回の編集パスでまとめて行い、1件ごとに再 lint しない（機械 lint は安価なので編集のたびに回してよい）。
- **ゲート G2**：lint 全層パス（初回）。不合格は該当スライドだけ差し戻す。

成果物：`slides.md`（内容の正）、`slides.html`（完成スライド）、`lint-report.md`

### フェーズ3：検証

- コールドリード：作り手とは別のパス（別のエージェントまたは別人格）で実施する。渡すのは読み手像と完成形だけで、作り方の経緯や意図の説明は渡さない。範囲は**物語の受信確認に絞る**（anti-slop 全項目の再実施はしない。大原則7）。読み手役は通読して「自分が受け取った物語」を主張の列として書き出し、それを `storyline.md` と照合する。ズレた主張・読み違えた接続・図から主張が言い直せなかったスライドを所見として記録する。作り手の自己点検では代替しない。
- 数値・事実を出典と照合する。仕組みや製品を説明する資料では、主張を仕様・一次資料（この基盤なら core の現行文書）と照合する（指摘ナレッジ F6）。検証の力点は主型リードが決める（例：成果・検証報告型なら数値と方法の照合、決断提案型なら決めてほしい事項の明確さ、ピッチ／招請型なら ask と入口の有無）。
- 副型リードは、副型の成功条件が満たされているかを最後に確認する。
- **ゲート G3**：人間が最終承認する。

成果物：確定版スライド、検証メモ
