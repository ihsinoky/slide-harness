# 再設計案 v2 — 類型診断＋型リード制（mob 方式）

状態：設計案（未実装）。根拠：型類型調査（2026-11-15、Speaker Deck／ドクセルの高閲覧デッキの帰納＋プレゼン理論。主軸＝「読み終えた後に読み手が行う仕事」、7類型）。
試走1号の事後判定（主型＝②ピッチ／招請型、副型＝⑦視点提示型、カバー率半分強）が直接の動機：型を後付けで判定するのではなく、最初に診断して型の観点で作る。

## 1. AI-DLC の理解の訂正・補完（ユーザーの構想に対して）

ユーザーの構想：「類型ごとのリードをエージェントとして定義し、主・副ともに自分のミッション・観点をもとにプロセスを実行する」。

AI-DLC（AWS の AI-Driven Development Life Cycle）の実際の設計に照らすと、2点の補正が要る。

1. **mob は「各エージェントが全プロセスを並走する」形ではない。** AI-DLC の Inception Mob／Construction Mob は、段階ごとに専門ロールが集まって協働し、人間も mob の一員として参加する形。エージェント（ワークフローの各ステージの定義）はステージ固有で、入力と成果物が定義されている。型リードがそれぞれ全プロセスを独立に回すと、成果物が競合して収拾がつかなくなる。
   → 本設計では、型リードは「全フェーズを通して変わらないミッションと観点を持つロール」として mob に常駐させる（これは AI-DLC のステージ固有エージェントからの意図的な逸脱で、型のミッションはフェーズを跨いで保持すべきものだから）。ただし実行の主導権は主型リード1つに寄せ、副型リードは貢献とレビューに徹する。
2. **類型診断に相当するのは、AI-DLC では Inception の分析とワークフロー計画（adaptive workflow）である。** AI-DLC は作業の性質を分析してから、必要なユニット／ステージの構成を計画する。
   → 本設計の類型診断は「型を当てる」だけで終わらせず、**プロセス計画**（どのフェーズに力点を置くか、どの lint 項目を有効化するか、典型構成を足場として使うか）までを出力する。

AI-DLC からそのまま引き継ぐもの：段階ごとの人間の承認、成果物を共有ワークスペースに残して再開・差し戻し可能にすること、分析に基づいてワークフローを適応させること。

## 2. プロセスの形（v2）

### フェーズD：類型診断（新設、フェーズ0の前）

- 診断エージェント（型に中立）が、素材と依頼の初期情報から「読み手の仕事テスト」（この資料が成功したとき、読み手は具体的に何をした／何を持ち帰った状態になるか）で主型1つ・副型0〜1つを提案する。
- 成果物：`type-diagnosis.md` — 主型／副型、各々の根拠（読み手・成功条件）、**棄却した他の型とその理由**、プロセス計画（力点フェーズ、有効化する型固有 lint、典型構成を足場にするか）。
- **ゲート GD**：人間が診断を確認する。priority-map のスコア基準が型で決まるため、診断の誤りは後段全部に伝播する。ここは独立ゲートとし、G0 とは混ぜない（ただし提示は intent の叩き台と同時でよい）。

### 型リード（7エージェント）

各型リードは環境非依存のロール定義として `core/type-leads/` に置く（バインディングはこれを各環境のエージェント定義に写す）。各定義は次の5節で構成する。

1. **ミッション**：その型の成功条件（読み手の仕事）を1文で
2. **観点**：その型で内容を見るレンズ（問いの一覧）
3. **スコア基準**：priority-map で何を上位に置くか
4. **典型構成と疑問チェーン**：スライドの並びの足場と、読み手の疑問の進み方
5. **型固有 lint**：その型特有の失敗パターン（隠蔽・誇張・粉飾など）を検査項目にしたもの

| # | 型リード | ミッション（成功条件） | スコア基準の芯 | 型固有 lint の芯 |
|---|---|---|---|---|
| ① | 決断提案 | 決断者が採否と資源配分を決められる | 代替案比較と反対論への回答 | 不利な代替案・前提の隠蔽、効果予測の実績化 |
| ② | ピッチ／招請 | 資源提供者・参加候補者が「出す／加わる」を前向きに判断する | 対象の実態の具体性と参加意欲 | 市場規模の水増し、参加後に効く情報の欠落 |
| ③ | 状況把握 | 関係者が計画との差分を掴み、介入要否を判断できる | 基準線との差分の大きさ | watermelon reporting（外は緑・中は赤）、活動量での代替 |
| ④ | 成果・検証報告 | 評価者が事前の目標／仮説への達成を判定できる | 評価材料としての完全さ（未達も上位） | 指標の事後的すり替え、未達の埋没、方法の不透明化 |
| ⑤ | 原因究明・学習 | 同業者が因果モデルと教訓を持ち帰り、変えることが決まる | 因果の再構成への寄与 | 責任追及への変質、単一原因への決めつけ、検証不能な教訓 |
| ⑥ | 説明・教育 | 学習者が使える概念モデルを持ち帰る | 理解のボトルネック度 | 前提の飛ばし、密度過多、誤った単純化の放置 |
| ⑦ | 視点提示・ビジョン | 読み手の見方・判断基準が変わる | フレームの新しさと一貫性 | 標語化、フレームに合う事例だけの選別 |

### フェーズ0〜3 の回し方（mob 方式）

- **フェーズ0 意図**：主型リードが intent と priority-map を主導する（スコア基準は主型のもの）。副型リードは、副型の観点から候補を追加し（priority-map に「副型候補」と明記）、副型の失敗パターンの警告を添える。
- **フェーズ1 構成**：主型リードが典型構成を足場に疑問チェーンを組む。副型リードは、副型の要素を「独立パートとして置くか／各スライドに織り込むか」を提案し、チェーンの切れ目をレビューする。
- **フェーズ2 生成＋lint**：生成は主型リードの構成で進める。lint は生成と別パスを維持し、3層で判定する — 共通 anti-slop（中立の検査パス）、主型 lint、副型 lint（各型リードの型固有項目）。不合格は該当スライドだけ差し戻す。
- **フェーズ3 検証**：検証の力点は主型が決める（例：④なら数値と方法の照合、①なら決めてほしい事項の明確さ、②なら ask と入口の有無）。副型リードは副型の成功条件が満たされているかを最後に確認する。
- **ゲート（GD／G0／G1／G3）**：人間の承認。各ゲートでは主型リードが案を提示し、副型リードは異論・懸念があれば併記する（mob のレビューとしてゲート資料に残す）。

### 主・副の競合ルール

- 副型の要素は、主型の成功条件を損なう場合は落とす。判断は主型リードが行い、落とした要素と理由を成果物に記録する。
- 主型リードと副型リードの意見が割れて主型側でも決められないものは、ゲートで人間に上げる（勝手に決めない）。
