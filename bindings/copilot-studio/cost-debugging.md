# コストの内訳とデバッグ（GitHub Copilot ハーネス）

2026-11-17 調査。対象の事象：このリポジトリを Copilot Studio（GitHub Copilot ハーネス）に移植し、スライド1本の作成で約600クレジット（約1,000円）を消費した。

## まず課金の仕組みを押さえる

- このハーネスは標準ハーネスのレートカード（生成回答2クレジット等）では課金されない。**従量制**で、モデルのトークン、ツール呼び出し（Knowledge 検索や MCP を含む）、ハーネスのランタイム自体にクレジットがかかる
- 作成・プレビュー・テスト・評価も課金される（公開後だけではない）。M365 Copilot ライセンスによる相殺（ゼロレーティング）はこのハーネスには適用されない
- Microsoft の計画バンドは、軽いタスクで約100〜300、中程度で300〜500、重いタスクで500超（クレジット／タスク）。推論モデル（Opus 級）では、1メッセージで400クレジットを超える例も報告されている
- つまり600クレジットは「重いタスク」のバンド内であり、異常とは限らない。ただし、無駄な試行錯誤が混ざっているかは切り分けられるし、混ざっていれば大きく下げられる

## デバッグの手順（見る場所は3つ）

### 1. アクティビティトレース（Preview タブ）
GitHub Copilot ハーネス専用のデバッグ表示。End user preview をオフにしたメイカー表示で、メッセージごとに処理のノードが出る。

- ノードの種類：Knowledge／Ran action／Tool／Connector／Flow／Skill／Error／Complete。各ノードで入力・出力・所要時間・エラー詳細が見られる
- 見るべき点：
  - **Error ノードの有無と内容**（認証失敗、タイムアウト、ツールが見つからない等）
  - **同じツールの繰り返し呼び出し**：失敗→言い換えて再試行→別手段、のループがそのまま見える
  - **Skill ノードの実行範囲**：想定外のスキルが何度も実行されていないか
  - **Knowledge ノード**：どのソースを何回検索したか

### 2. Preview の History（Credits used 列）
- インタラクションごとの消費が見える。どのフェーズ（生成か、lint の往復か、検証か）で食ったかを特定する

### 3. Monitor と管理センター
- エージェントの Monitor ページで総量を確認する
- Power Platform 管理センター → ライセンス → Copilot Studio でプール全体を見る。エージェント単位の月次上限・通知しきい値・Stop usage の設定があるので、デバッグ中は上限を低く設定しておく
- 会話トランスクリプト（スナップショットのダウンロードや Dataverse）でも、ツール呼び出し回数をオフラインで数えられる

切り分けの進め方：まず1本だけ、トレースを開いた状態でタスクを流し、Error と繰り返しを数える。次に History でフェーズごとの消費を割り、重いフェーズから直す。Evaluate に小さな標準ワークロード（例：G0→G1 だけ）を作り、修正前後のクレジットを測って回帰を見る。

## この移植で疑うべき原因（優先順）

### 1. 未対応・未接続ツールへの試行錯誤（最有力）
- 指示に「必ず lint_slides を呼べ」と書いてあるのに、MCP サーバーが未接続・認証失敗・タイムアウトだと、エージェントは失敗→再試行→代替手段の探索を繰り返す。各ループは大きなコンテキストでの推論1回分なので、数回の空転で数百クレジットになりうる
- 対策：
  - ツールが実際に呼べることを、トレースの Tool ノード成功で確認してから指示に組み込む。未接続の間は、ツールと指示側の参照を両方外す
  - 指示に失敗時の上限を明記する（例：同じツールの再試行は2回まで。それ以上は止めて人間に報告する）
  - MCP ツールの説明と入力スキーマを正確に書く（エージェントの探索コストが下がる）

### 2. コンテキストの大きさ × ステップ数
- core の文書群とテンプレートは大きい。スキルと Knowledge の両方に同じ内容を入れると二重に読む。ステップごとにコンテキストを読み直す構造なので、総消費は「1ステップの単価 × ステップ数」で決まる
- 対策：指示と知識の重複をなくす（指示系はスキル、素材だけ Knowledge）。テンプレートはレンダリング時にだけ参照させる。1セッションで全フェーズを走らせず、フェーズごとにセッションを分けると、コンテキストも失敗時の再実行範囲も小さくなる

### 3. モデル単価
- このハーネスは高度な推論モデルを使う。Build でモデルを選べる場合は、評価セットで品質を見ながら軽いモデルも試す

### 4. フックの空転
- フックは fail-open（落ちても素通り）だが、フック自体のワークフロー実行は消費する。エラー続きのフックは、止めずに消費だけ増やす
- 対策：デバッグ中はフックを無効化して切り分け、安定してから戻す

### 5. 作成・テスト段階の消費の混入
- 移植作業中のプレビューや評価の消費が「1本分」に混ざっていることがある。History の時刻とセッションで、本番相当の1回の実行だけを抜き出して測り直す

## 出典（2026-11-17 確認）
- Microsoft Learn「Use the activity trace to debug your agent (Microsoft Copilot)」：トレースの開き方、ノードの種類、ツール実行とエラーのデバッグ
- Microsoft Learn「Overview of usage-based billing」系の課金ドキュメント、および Copilot Credit の見積もり・最適化に関する公開資料：従量制の内訳（トークン／ツール／ハーネス）、計画バンド（軽100〜300／中300〜500／重500超）、History の Credits used 列と Monitor での実測という見積もり方法、M365 Copilot ライセンス相殺の対象外であること
- 技術系メディアの検証記事：推論モデル使用時に1メッセージ400クレジット超の例、作成・テスト段階から課金されることの確認
